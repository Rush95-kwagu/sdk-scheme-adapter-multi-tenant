Hub — réseau, DHCP, NAT

Point qui bloque le plus souvent le premier boot Talos. Principe générique : si l’hôte a deux interfaces dans le même /24 (NIC physique + pont VM), le noyau répond DHCP et route vers les VM par la NIC. La VM, branchée seulement sur le pont, ne voit rien.

Symptôme Talos : IP vide, CONNECTIVITY FAILED, STAGE: Booting, Discover DHCP sans Offer.

Cible propre : une seule adresse du LAN sur le pont, NIC physique en port du pont. Contournement : routes hôte /32 vers le pont + SNAT.

Mono DFSP vs overlay valeur ajoutée

Le SDK officiel (image mojaloop/sdk-scheme-adapter:v24.9.0, sans overlay) est conçu pour un DFSP par processus. Deux flags distincts existent ; les mélanger est la principale source de confusion.

Les trois modes à ne pas confondre

SDK officiel 1:1 SDK officiel MULTI_DFSP=true Overlay PM4ML_MULTI_TENANT=true
Agents PM4ML 1 websocket MGMT_API_WS_URL Toujours 1 agent N websockets MGMT_API_WS_URLS
Identité Hub (certs, JWS, Hydra) 1 DFSP_ID Toujours 1 identité PM4ML N identités (store par dfspId)
NOTIFY agent restart() inbound + outbound Idem restart global Upsert mémoire, pas de restart
Chemin inbound Hub /parties, /quotes Peut exiger /{dfspId}/parties (préfixe backend) Reste /parties (Host = tenant). MULTI_DFSP forcé à false
Chemin outbound CBS → SDK /transfers (pas de préfixe) Optionnel selon backend Obligatoire /{dfspId}/transfers sinon 404
Backend CBS Un BACKEND_ENDPOINT Concatène backendEndpoint/{dfspId} (un CBS qui multiplexe par path) Un backend par tenant (NOTIFY), sans concaténer le path Hub
Combien de stacks Compose 1 SDK + 1 agent Toujours 1 SDK 1 SDK overlay + N stacks agent/Vault

Que fait vraiment MULTI_DFSP dans le SDK mono ?

Dans le code officiel, MULTI_DFSP n’ouvre pas un second agent et ne stocke pas N certificats. Il change le routage de chemin :

  • Inbound : le premier segment d’URL est interprété comme dfspId ; le Hub devrait appeler /gto/parties/… au lieu de /parties/….
  • Vers le CBS : le SDK concatène {BACKEND_ENDPOINT}/{dfspId} (ex. un connecteur unique avec un tenant par préfixe).
  • Un seul ControlAgent, un seul DFSP_ID d’environnement, un seul restart à chaque NOTIFY.
Un SDK officiel avec MULTI_DFSP=true ne remplace pas N stacks 1:1. Coller deux DFSP_ID / deux FQDN dans le même processus mélange les certs (erreur type SAN *.bftlabs.org vs Host DFSP). Le toolkit historique « multi-DFSP » = N Compose (ports 4000, 4100, 6000…), pas un process partagé.

Quand rester en SDK dédié

  • DFSP prod sensible (lab : moov sur :6000) hors overlay tant que le cutover n’est pas validé.
  • Besoin d’isoler la panne : un crash SDK overlay touche N caisses.
  • CBS / WAF pas encore prêts pour le préfixe outbound /{dfspId}/.

Agents PM4ML

L’agent (mcm-agent) n’échange pas de FSPIOP. Il enrôle le DFSP auprès du MCM Hub, stocke les PEM dans son Vault, et pousse la conf au SDK en websocket :4004 (CONFIGURATION.READ / NOTIFY).

Un agent = un DFSP (Hydra, Vault, FQDN, certs). En multi-tenant les agents restent 1:1 ; seul le SDK est partagé.

DfspConfigStore

Map mémoire dfspId → backend, endpoints Hub, JWS, PEM outbound. upsert à chaque NOTIFY. applyTo fusionne le slice dans la conf de cette requête. IDs placeholder / mojaloop ignorés. Un restart du conteneur vide le store jusqu’au prochain READ.

JWS : signature outbound et validation inbound Hub (hors GET, hors PUT /parties par défaut). mTLS outbound vers extapi avec le cert client du tenant. mTLS inbound = ssl_verify_client au WAF.

Clé outbound : lab/.env → OUTBOUND_API_KEY_ENABLED=true|false et OUTBOUND_API_KEY=…. Header accepté : X-API-Key ou Authorization: Bearer. Rebuild : just build.
