Onboarding d’un DFSP

Procédure à suivre dans l’ordre, de la fiche jusqu’au nginx. Une étape n’est finie que lorsque le résultat attendu est affiché. On ne passe pas à la suivante avant. C’est le déploiement Docker sur le nœud SDK (un dossier par DFSP). Un cluster Kubernetes participant n’utilise pas ces étapes : chart dfsp/, voir docs/participant/installation.md.

2. Choisir les ports

Sur le nœud SDK, depuis le dossier personnel (là où se trouve justfile) :

cd ~

Résultat attendu : la liste des ports déjà pris, puis un ou plusieurs blocs « Bloc libre ». Chaque bloc donne cinq nombres. Recopie-les dans la fiche.

Ligne de la ficheLigne du blocÀ gauche des deux-points dans le compose

Le nombre après les deux-points (5000, 5001, 5040, 3003) ne change jamais. On ne change que le nombre de gauche.

Pour ne proposer qu’un bloc à partir d’un numéro (par exemple après la série déjà en service) :

just ports 10300 1

Prendre un bloc dont les cinq ports sont marqués libres. Ne pas réutiliser un port listé plus haut comme « occupé ».

Toujours dans deploy/, avant ./manage.sh. Ces unset empêchent le terminal de réutiliser le secret ou le nom d’un autre DFSP.

unset DFSP_ID DFSP_FQDN HUB_IAM_PROVIDER_URL MCM_SERVER_ENDPOINT

up aligne d’abord les volumes Vault sur l’utilisateur 100:100, puis démarre. Résultat attendu : la ligne manage.sh: chown 100:100 on …, puis les conteneurs créés, sans permission denied.

./manage.sh ps
./manage.sh logs vault-init
  • sdk-vault-init-… finit par Exited (0).
  • mcm-agent-… passe healthy (attendre jusqu’à une minute).
  • sdk-scheme-adapter-… est Up.

Sans CBS, à la place de ./manage.sh up -d :

./manage.sh --profile simulator up -d

Si les logs Vault disent permission denied sur /vault/data alors que ./manage.sh up a bien affiché le chown, arrêter et relancer l’init (ne pas supprimer les volumes) :

./manage.sh stop
./manage.sh rm -f vault-init
./manage.sh up -d

Les unset effacent DFSP_ID dans ce terminal. Pour la commande suivante, retaper la ligne A. Si l’agent répète Vault is sealed :

export DFSP_ID=banque-test
docker start sdk-vault-init-$DFSP_ID

La réponse doit être la ligne A, rien d’autre. Si c’est l’identifiant d’un autre DFSP, les unset ont été oubliés : refaire les unset, puis ./manage.sh up -d --force-recreate mcm-agent.

Sur le WAF (ops@WAF-AGG). Vérifier d’abord que le WAF voit le nœud SDK. -c attend un nombre, puis l’adresse. Pas de http://.

Résultat attendu : 2 réponses, 0 % de perte. Sinon, ne pas éditer nginx : le trafic n’arrivera pas au SDK.

Deux noms, vers l’adresse publique du WAF (la même que moov.ext.openmfi.org). Pas vers 172.25.2.117 : le Hub ne joint pas le nœud SDK.

ops Compose 1:1

Après reboot — unseal Vault (nœud SDK)

Sur le nœud Docker (<SDK_HOST>), chaque DFSP a son Vault fichier (sdk-vault-<fspid>). Au reboot de la VM (ou restart du démon Docker), Vault redémarre sealed. Le job vault-init a restart: "no" : il ne se relance pas seul. L’agent crash alors avec Vault is sealed.

Ne pas faire docker volume rm …vault-data… ni vault operator init à nouveau : les clés / role-id sont déjà dans le volume vault-creds. Un wipe détruit la CA et les secrets PM4ML du DFSP.

Que fait vraiment MULTI_DFSP dans le SDK mono ?

Dans le code officiel, MULTI_DFSP n’ouvre pas un second agent et ne stocke pas N certificats. Il change le routage de chemin :

  • Inbound : le premier segment d’URL est interprété comme dfspId ; le Hub devrait appeler //parties/… au lieu de /parties/….
  • Vers le CBS : le SDK concatène {BACKEND_ENDPOINT}/{dfspId} (ex. un connecteur unique avec un tenant par préfixe).
  • Un seul ControlAgent, un seul DFSP_ID d’environnement, un seul restart à chaque NOTIFY.
Un SDK officiel avec MULTI_DFSP=true ne remplace pas N stacks 1:1. Coller deux DFSP_ID / deux FQDN dans le même processus mélange les certs (erreur type SAN *.bftlabs.org vs Host DFSP). Le toolkit historique « multi-DFSP » = N Compose (ports 4000, 4100, 6000…), pas un process partagé.

Agents PM4ML

L’agent (mcm-agent) n’échange pas de FSPIOP. Il enrôle le DFSP auprès du MCM Hub, stocke les PEM dans son Vault, et pousse la conf au SDK en websocket :4004 (CONFIGURATION.READ / NOTIFY).
